### A. 通用架构还能提升的（不换模型，按性价比排序）

**架构合计现实上限：~86-88%**。其中 1/2/5 三项（纯读路径+工序，零重摄）就能从 82.2 打到 ~85。

### B. 模型天花板（deepseek-v4-flash 的极限，架构修不动）

1. **抽取压缩本性**：a3"摘要式 value"是模型行为，两轮 few-shot/规则措辞 0/13 修复证明已触 prompt 工程的天花板。载荷 verbatim/逐条属性要换更强的抽取模型（或专用微调）才能根本解决。这类顽固残余 ~15-20 题（3-4pp）。
2. **语言指令依从率**：钉死语言后仍 20-30% 漂移——flash 对长 prompt 尾部指令的依从极限。代码层语言检测能兜底（那是架构修复），但模型端无法根治。
3. **judge 同源税**：抽取/答案/判卷同一 flash；judge 方差 ±2-3 题/轮（两轮翻转实证）+ 完整性偏严（近逐字等价判 0）。这是分数的自洽性折扣，换强 judge 或多数投票可回收 ~1pp，但也改变口径。
4. **推理勇气**：部分 d 类（e831120c 口径选择、46a3abf7 歧义读法）是 flash 在歧义证据前的校准问题——但注意其中相当部分是 LongMemEval 金标宽松造成的"我们更严谨反而扣分"，换强模型未必更好（强模型更精确、金标更粗糙，可能更糟）。

### C. 设计能力边界（我们主动选择的代价，不该当缺陷修）

1. **容量 vs 结构**：k=30/48 行预算这条路已到收益递减点（b 类 16% 且残余分散）。下一步聚合只能靠 roll-up 层/图计数头——而图计数头在本轮 89 道错题里依旧零使用（分组渲染的"header count"只在题面恰好像素级对上时有用）。**结构化聚合是正确方向，但它是一个新层，不是调参**。
2. **宁少勿滥 gate**：12 facts/session + 白名单——旁插细节丢失有一部分是设计代价。旁插保全与宁少勿滥存在内在张力，只能靠"事件类语句绕过 maxFacts 预算"这类精细规则缓解，不能全开。
3. **标而不裁 + 人在回路**：single-cardinality 状态机把冲突降级 tentative 等人审——benchmark 里没人审，只能靠 rule 3 启发式兜底（a2f3aa27 型两轮未愈）。这是哲学代价：**离线分数买不到人审的对价**。
4. **单一 SQLite + 暴力扫**：ANN 不做（<10 万语句纪律）——速度/规模边界明确，检索质量靠混合评分而非索引，k 竞争的战场永远在窗口里。
5. **同源判卷口径**：对外报分要带"extractor=judge=deepseek-v4-flash"星号——这不是我们的缺陷，是协议的一部分。

### 总判断

- **+8pp 的构成**：Jev k=30（多会话 b 类 34%→6%）+ 英文层（抽取覆盖+词面匹配）+ rule7 拒答修复（3 道 _abs 翻正）为主力；纪律过冲吃掉 ~2pp 掩盖了真实收益。
- **89 道错题的可救性**：读路径可修 ~30%（d+b 大部）、重摄可修 ~40%（a 类，但需要**专项保全**而非重跑同 prompt——两轮同错已证明）、judge/数据集固有 ~10%、模型天花板挤压剩余 ~20%。
- **天花板预测**：flash + 本架构的现实极限 ≈ **88-90%**（架构改满 + 抽取专项全生效的理想情形）。最后 5-8%（顽固压缩 + judge 税 + 数据集噪声 + 金标宽松反咬严谨答案）是当前的硬底，**要破 90 得换更强的抽取/判卷模型——那已经不是架构问题**。
- 反过来说一个诚实的观察：82.2% 是在"混合库 + 纪律过冲"两个拖累下拿到的。**干净重摄 + 纪律边界之后，同样的 flash 可能已经站在 85 附近**——这两件事是下一轮最便宜的两步。
