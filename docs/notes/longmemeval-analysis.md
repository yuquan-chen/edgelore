# edgelore · LongMemEval ORACLE 评测报告与架构分析

> 日期：2026-09-19
> 配置：deepseek-v4-flash-0731（chat）+ qwen3.7-text-embedding（embedding），均走狗路由
> 数据集：LongMemEval ORACLE（500 题 / 940 会话 / 仅金证据会话）

| 指标 | 值 |

## 三、逐能力错误分析

### 3.1 拒答能力 76.7% —— 最强项 ✓

记忆不够时诚实说"不知道"，不编造。30 题拒答题中 23 题正确识别为不可回答。**这是 gate 设计和 ask 拒答机制的直接验证。**

剩余 7 题失败原因：deepseek-flash 的思考过程偶尔吃掉输出预算（已修复 maxTokens → 16000）。

### 3.2 知识更新 62.5% —— 第二强 ✓

事实发生变更时，系统正确引用了最新的 accepted 值而不是被 superseded 的旧值。**这是冲突治理机制的直接验证。**

剩余 12 拒答：检索没有召回相关记忆（维度清单太长稀释了检索效果）。

### 3.3 单会话用户 67.2% —— 第三强 ✓

基础用户事实（学历、品牌、地点）的召回和引用正常。6 个错误：维度 key 漂移导致检索漏了部分记忆。

### 3.4 单会话偏好 36.7% —— 弱

偏好类记忆能存但**抽取粒度不够细**。比如"我喜欢简洁的回复，不要废话"被抽成一条泛化的偏好记忆，而没有拆成"语言：中文"和"风格：简洁"两条。导致回答时召回的记忆不够精准。

### 3.5 多会话推理 16.5% —— 弱

**核心病因：计数不全。** 看真实错误：

| 题目 | 金标准 | 我们答 | 原因 |
|---|---|---|---|
| 今年参加了几场婚礼？ | 3 场 | 1 场 | 检索只召回了 1 条婚礼记忆，漏了另外 2 条 |
| 总共筹了多少钱？ | $5,850 | $250 | 只找到了 1 条筹款记录，漏了其他 |
| 买了几件家具？ | 4 件 | 1 件 | 同上 |
| 保养了几辆自行车？ | 2 辆 | 1 辆 | 一条被 superseded 排除了 |

**两层原因**：
- **检索层**：k=10 限制了召回量，答案散在多条记忆里时必然漏
- **治理层**：superseded 的记忆默认被排除 → 历史事件的计数必然偏少

### 3.6 时间推理 14.2% —— 最弱之一

**三层根因**：

| 层级 | 问题 | 影响 |
|---|---|---|
| 检索层 | 语义检索不感知时间（"上个月"≠ 语义相似度） | 找不到时间范围内的记忆 |
| 数据层 | 存的是"说话时间"，不是"事件时间"（"上周五开会"的 created_at 是说话日期） | 日期本身可能就是错的 |
| 回答层 | 回答 prompt 没引导模型做日期计算；68% 的题直接拒答 | 有数据但没用 |

### 3.7 单会话助手 7.1% —— 最弱

**根因是设计缺口，不是 bug**：我们的抽取 prompt 明确写了 "attribute facts to the USER's life/project (the assistant only helps)"——**AI 自身的有价值结论被系统性丢弃了**。

但 AI 的结论恰恰是用户决策的重要依据："PostgreSQL 比 MongoDB 更适合这个场景"是 AI 的推荐，但对用户来说是重要的项目决策。**不存 AI 结论 = 丢掉了一半的对话价值。**

49 个拒答里，大部分是题目问"AI 推荐了什么/说了什么"——我们的库里根本没有这类记忆，当然答不出来。

## 四、架构级根因分析

上面的表面原因背后，是**四个架构级的设计问题**：

### 4.1 写入管线的"宁少勿滥"过度过滤了事件记忆

Gate 把"参加了婚礼""买了烟熏炉""去了音乐会"等**一次性事件**归类为"不值得长期记住"而过滤。但 LongMemEval 恰恰考这些事件。

**本质**：我们定义"值得记"的标准偏向"稳定属性"（偏好、身份、规则），忽略了"时间线上的事件"也是记忆的重要组成。

**修法**：gate 的白名单增加"event"类型（有时效性但有价值的事件），或者给"一次性事件"设一个短保质期而不是直接拒绝。

### 4.2 AI 回复被系统性丢弃

这是设计决策（"记忆 = 用户的事实"），但忽略了 AI 的结论也是用户决策的依据。

**修法**：抽取 prompt 去掉 "the assistant only helps" 的偏向，让模型评估所有有价值的对话内容（不管谁说的），用署名链记录来源。

### 4.3 检索层不感知时间和聚合

| 问题 | 现状 | 需要 |
|---|---|---|
| 时间查询 | 语义检索找不到"上个月的事件" | 时间范围过滤 |
| 计数查询 | k=10 只召回部分 → 计数不全 | 聚合查询（COUNT per dimension） |
| superseded 排除 | 检索默认排除 superseded → 历史计数偏少 | 历史查询包含 superseded |

### 4.4 维度漂移导致检索信噪比下降

同一个概念（"负责人"）被存为 owner / manager / projectLeader 三个维度 → 检索"负责人"时可能只命中其中一个 → 另两个维度的记忆被漏掉。别名守卫（前缀匹配）只能部分缓解。

**修法**：M5 生命周期设计中已规划（维度别名表 + 后台合并），但优先级需要提升。

## 五、局限性

| 局限 | 说明 |
|---|---|
| 裁判 = 参赛模型 | deepseek-flash 既做抽取又做判分，有同源偏差。官方用 GPT-4o 判卷，分数可能不同 |
| ORACLE 是最容易的配置 | 只有金证据会话。S 配置（~115K token）会更难 |
| 模型能力天花板 | deepseek-v4-flash 是轻量模型。换 GPT-4o 级别的模型分数会显著提升——但那是模型的能力，不是框架的能力 |
| 单次运行 | 未做多次运行的方差分析（temperature=0 应该是确定的，但中转站不稳定可能引入波动） |

## 六、改进路线图（按投入产出比排）

| 优先级 | 改进 | 影响的题数 | 成本 | 预期提升 |
|---|---|---|---|---|
| **P0** | 拒答门槛调优：有相关记忆时不轻易说"不知道" | ~100 题不当拒答 | prompt 调优 | 总分 +15~20% |

## 八、对产品定位的影响

跑分结果验证了之前的产品判断：

- **强项（拒答 76.7%、知识更新 62.5%）验证了"记忆治理"的产品定位**——记对了、错了能改，这两个场景我们的设计确实有效
- **弱项（助手 7.1%、时间 14.2%、计数 16.5%）暴露了"覆盖不全"的问题**——不是治理机制本身有 bug，是**管线没有覆盖到这些场景**（AI 回复没入库、时间没被利用、superseded 被排除）

**改进方向不是放弃治理，而是扩大治理的覆盖范围**：从"只治理用户事实"扩展到"治理所有有价值的对话内容"，从"只支持当前状态查询"扩展到"支持历史计数和时间推理"。
